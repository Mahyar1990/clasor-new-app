# نگاشت مرجع به کلاینت موجود

## مشخص‌کردن قرارداد

منبع را با revision ثابت و مقصد را با branch فعلی ثبت کن. مرجع باید توکن‌ها، نمونهٔ تعاملی و رفتار موردنظر را قابل بررسی کند. دستور جاری و قواعد مقصد تقدم دارند. اگر snapshot قدیمی با کد فعلی متفاوت است، اختلاف را ثبت و تصمیم جاری را اعمال کن.

| موضوع | آنچه در مقصد باید پیدا شود | خروجی نگاشت |
| --- | --- | --- |
| توکن و CSS | رنگ، فضا، type scale، semantic role، pipeline تولید | منبع واحد توکن و روش build |
| کنترل و overlay | دکمه، field، Select، menu، dialog و sheet | جزء مشترک و wrapper واقعی مصرف‌کننده |
| route و layout | پوسته، صفحات مستقل، sidebar و portal host | محل اعمال تغییر و state ماندگار |
| هویت و ترجیح | session، profile، theme store و logout | دادهٔ واقعی و سازگاری تنظیم ذخیره‌شده |
| داده و عملیات | query، mutation، مجوز و lifecycle درخواست | callback/API فعلی و نتیجهٔ قابل مشاهده |
| نمونه و تست | catalogue یا Storybook و ابزار مرورگر | مثال مستقل و آزمون مسیر واقعی |

برای React همراه Tailwind، candidateهای کلاس state، dark و motion باید به‌صورت قابل استخراج در pipeline مقصد باشند. مسیرهای content scanning، custom variant و ترتیب layer را بررسی کن. در استک دیگر، همین رفتار را به مکانیزم بومی آن نگاشت کن.

نصب dependency، جایگزینی design-system provider یا جابه‌جایی کل routing فقط وقتی انجام شود که دامنهٔ مجاز کار آن را می‌خواهد. import alias، CSS متغیرها، registry componentها و icon set را هنگام کپی جزء در نظر بگیر.

## موجودی صفحه

برای هر خانوادهٔ مسیر، حالت مهمان/واردشده و نقش‌های مؤثر را ثبت کن. روی صفحه، کنترل‌های تکراری و تمام گزینه‌های منو و زیرمنو، دیالوگ، تب، picker و action شناور را دنبال کن. iframe، portal و مسیر ورود مستقیم جزو صفحه‌اند.

از جدول کوتاه با ستون‌های «مسیر و state»، «کنترل»، «جزء مقصد»، «قرارداد مرجع»، «اختلاف» و «وضعیت بررسی» استفاده کن. ساختار جدول را با اندازهٔ تسک تطبیق بده. N/A و بررسی‌نشده را با علت ثبت کن. تعداد ترکیب‌ها را به تعداد مسیرها تقلیل نده.

## اجرای مرحله‌ای

اول یک مسیر نماینده با تعامل واقعی را کامل کن تا اتصال توکن، wrapper و build بررسی شود. سپس مصرف‌کنندگان مشترک و خانواده‌های مسیر را با همان قرارداد مهاجرت بده. کنترل‌های بی‌اثر یا فقط کاتالوگی به معنی پایان آن مرحله نیستند.

برای جزء مفقود، عمومی‌ترین بخش موردنیاز را در لایهٔ UI استخراج کن. orchestration نقش، داده و business flow در مالک محصول بماند. مثال کاتالوگ از همان implementation استفاده کند و با fixture مستقل stateهای لازم را نشان دهد.

رفتارهای create/update/delete و retry باید همچنان به API معتبر قبلی برسند. در صورت خطای جزئی یا تغییر هم‌زمان، وضعیت سازگار و پیام دقیق حفظ شود. دادهٔ قدیمی، URLهای ذخیره‌شده و snapshotها را در دامنهٔ تغییر بررسی کن.

## انتقال دارایی

بستهٔ اسکیل، دستور کار است. برای اجرای جزء، dependencyها، توکن‌ها و CSS آن هم لازم‌اند. فونت یا تصویر محصول را همراه مجوز معتبر منتقل کن. اگر مجوز دارایی مبدأ در دسترس نیست، از دارایی مجاز مقصد استفاده و اختلاف typography/هندسه را اندازه‌گیری کن.

fixture، session ساختگی و شبیه‌سازی تأخیر به پروژهٔ تولیدی منتقل نشوند. سرویس موجود مقصد مالک authentication، authorization، upload و persistence می‌ماند.

برای به‌روزرسانی نسخهٔ اسکیل نصب‌شده، پوشهٔ کامل نسخهٔ جدید را با قبلی مقایسه کن. تغییرهای محلی مقصد و فایل‌های حذف‌شدهٔ نسخهٔ جدید را مشخص کن. کپی روی پوشهٔ موجود ممکن است فایل بازنشستهٔ نسخهٔ قبلی را نگه دارد. پس از تطبیق، فایل‌های هر بسته با revision انتخاب‌شده یکسان باشند و اعتبارسنجی روی خودِ کپی مقصد اجرا شود.
