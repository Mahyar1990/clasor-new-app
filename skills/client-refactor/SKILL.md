# ریفکتور کلاینت با مرجع طراحی

از کد موجود و مرجع تعیین‌شدهٔ کاربر، یک نگاشت قابل اجرا بساز و تغییر را تا صفحهٔ واقعی مصرف‌کننده دنبال کن. دامنهٔ تغییر را از درخواست بگیر. رفتار فعلی محصول و آخرین تصمیم کاربر مبنای حفظ قراردادند.

## شروع در پروژهٔ مقصد

دستورهای پروژه، نسخهٔ فریم‌ورک، مسیرها، کتابخانهٔ UI، منبع توکن، احراز هویت، API و تست‌های موجود را بخوان. اگر مرجع طراحی در workspace دیگری است، مسیر و revision آن را مشخص کن. منبع مشاهده‌نشده را به‌عنوان بررسی‌شده معرفی نکن. برای استفاده از این اسکیل نیازی به سرویس خارجی یا runtime خاصی نیست.

برای انتقال، [نگاشت و اجرای مرحله‌ای](references/adoption.md) را بخوان. برای کنترل سازگاری، اتصال صفحه و تحویل، [راستی‌آزمایی](references/verification.md) را بخوان.

## اجرای کار

1. یک مسیر واقعی و وابستگی‌های مشترک آن را انتخاب کن. داده، مسیر موفق/خطا، فرم‌ها، مجوزها و عملیات وابسته به state را از محصول ثبت کن.
2. منبع استایل و تعامل مطلوب را با کنترل‌های موجود نگاشت کن. reuse، توسعهٔ API سازگار و استخراج جزء عمومی بر اساس نیاز مشاهده‌شده انجام شوند.
3. تغییر جزء، مصرف‌کنندگان آن، مثال مستقل و قرارداد را در همان تحویل پیش ببر. از ورودی معمول route و تعامل کاربر تست کن.
4. بعد از هر بخش، وضعیت مسیرهای تغییرکرده، خطاهای باز، رفتار حفظ‌شده و مرحلهٔ بعد را با شواهد نسخه مشخص کن. برای تغییر صرفاً بصری، قرارداد سرویس یا مدل داده را تغییر نده.

## مرزهای انتقال

پروفایل بصری باید در دسترس باشد، از دستور کاربر یا مرجع محلی خوانده شود. در صورت انتخاب زبان این مخزن، اسکیل glass-design-system قواعد بصری را فراهم می‌کند. برای کلاینت کلاسور، clasor-product-patterns رفتارهای دامنه را فراهم می‌کند. این نام‌ها گزینه‌های مکمل‌اند و اجرای این اسکیل به نصب آن‌ها وابسته نیست.

طرح جدید نباید handlerها را با mock جایگزین کند یا permission را از ظاهر نقش حدس بزند. API عمومی، deep link، دادهٔ ذخیره‌شده و رفتار retry را در تغییرات مربوط حفظ کن. تغییر استک، قرارداد backend یا دامنهٔ محصول به تصمیم صریح همان کار نیاز دارد.

خروجی هر مرحله باید روی برنچ و کامیت قابل شناسایی ثبت شود، مطابق مجوز همان کار. مرج، پوش و انتشار تابع درخواست کاربر هستند.
