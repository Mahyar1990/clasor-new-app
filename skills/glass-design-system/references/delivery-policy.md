# قرارداد رشد سیستم و تحویل

## DG-12 — جزء، نمونه و قرارداد

- برای هر بازنگری صفحه، تطبیق اجزای مشاهده‌شده با سیستم طراحی را انجام بده. جزء عمومی فقط داخل preview محصول دفن نشود.
- primitive و composition مستقل از محصول در لایهٔ UI؛ رفتار کسب‌وکار در ماژول محصول؛ داده و تعامل نمایشی در کاتالوگ بماند.
- قاب مشترک، جدول، فرم، هدر، سایدبار و modal composition هستند؛ template صفحه را با primitive اشتباه نگیر.
- API عمومی، حالت‌ها، استفادهٔ RTL، keyboard و responsive همراه جزء مستند شوند. ورود به صفحهٔ محصول جای مثال مستقل در کاتالوگ نیست.
- هر جزء جدید مثال مرتبط و قابل دسترس از منوی کاتالوگ داشته باشد. نمونه باید رفتار واقعی را نشان دهد، نه screenshot ثابت یا دکمهٔ بی‌اثر.
- انتخاب یک استایل مشترک، به معنی اصلاح تمام مصرف‌کنندگان مرتبط است؛ نسخهٔ قدیمی در داشبورد یا دیالوگ باقی نماند.

## DG-13 — یک منبع ظاهر

- رنگ، فاصله، متریال و حالت‌ها را از توکن/کلاس مشترک مصرف کن؛ override صفحه‌ای که همان جزء را متفاوت می‌کند ایجاد نکن.
- در مبدأ کلاس‌های Tailwind در `lib/design-system/classes.ts` قراردادند، JSON منبع توکن است و CSS توکن تولید می‌شود. CSS تولیدشده را دستی ویرایش نکن. این مسیرها در پروژهٔ دیگر باید به معادل موجود مقصد نگاشت شوند.
- در مبدأ `theme.css` فقط متغیر دارد؛ هندسهٔ کاتالوگ و پوسته کنار مالک خود است. ساختار مقصد را برای کپی نام فایل‌ها خراب نکن.
- قوانین مهندسی مبدأ: فایل React حداکثر ۲۰۰ خط فیزیکی، شناسهٔ صریح تست برای کانتینر/کنترل، شناسهٔ پایدار رکورد، حفظ barrel export هنگام تقسیم، ابزار Select موجود shadcn/Base UI، ویژگی‌های منطقی RTL. از فشرده‌کردن کد برای دورزدن حد خط استفاده نکن. این محدودیت‌ها را در پروژهٔ جدید فقط همراه پذیرش همین قرارداد فنی منتقل کن.

## DG-14 — شواهد و تحویل گیت

- قبل از تحویل، checks موجود مقصد را اجرا کن؛ در مبدأ `npm run ui:check`، `npm run lint`، `npm run build` و برای رفتار، سه suite مربوط به workspace به‌علاوهٔ آزمون متناسب لازم‌اند.
- خودِ رفتار را در مرورگر بررسی کن: RTL/موبایل، overflow، پنل‌های مستقل، overlay، focus/restoration، کیبورد، تاریک محلی و پورتال، error/disabled و تنظیمات حرکت/شفافیت مرتبط.
- آزمون درست باید نتیجهٔ قابل مشاهده یا invariant را بررسی کند؛ برای تغییر متن ساده، تستی که فقط همان متن پیاده‌سازی را تکرار کند نساز.
- محدودیت محیط یا fallback build را دقیق بنویس. موفقیت اتوماسیون، تأیید انسانی screen reader، کنتراست کامل یا usability نیست.
- تغییرات منطقی در برنچ معنی‌دار و کامیت مشخص قرار بگیرند. merge/push فقط با درخواست یا مجوز معتبر همان جلسه انجام شود؛ خود اسکیل مجوز دائمی انتشار نیست.
- پوشش را در هر دو جهت بررسی کن. هر کنترل صفحه باید به قرارداد سیستم نگاشت شود و هر تغییر سیستم باید در مصرف‌کنندگان واقعی مربوط اعمال شود. واردکردن کامپوننت در کاتالوگ، اجرای آن در صفحه را ثابت نمی‌کند.
- build نهایی را با CSS تولیدشده باز کن. وجود utilityهای تم، state و motion و رفتار صفحه را بررسی کن. نتیجهٔ dev و build جای یکدیگر گزارش نشوند. شکست محیطی build را با همان علت ثبت کن.
- پیش از مرج، وضعیت ریموت و ancestry را بررسی کن؛ merge بدون تغییر ناخواستهٔ درخت و push بدون force باشد. پس از ارسال، برابری HEAD و شاخهٔ ریموت و تمیزی working tree را تأیید کن. حذف شاخه یا تغییر تنظیمات سرویس از درخواست معمول push نتیجه نمی‌شود.
- عکس آزمایشی، خروجی تولیدی موقت، دادهٔ واقعی حساب و اطلاعات خصوصی وارد کامیت نشوند. گزارش نتیجه hash/نسخه و محدودهٔ بررسی را مشخص کند.
